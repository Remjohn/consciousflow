## 3. THE 8-SECTION UNIT FORMAT (CONSTITUTIONAL STANDARD)

Every unit generated by the Unit Instructor MUST contain exactly these 8 sections in this exact order. Omitting any section (unless marked optional) is a structural failure.

### Section 1: 🧠 THE SCIENCE (120-160 words)
The theoretical concept explained from First Principles. Must include:
- One contrastive UNLEARN statement (the false belief to discard)
- One cross-disciplinary analogy from the approved disciplines
- The "why" before the "how" — explain WHY this matters to the CCP architecture

### Section 2: 🧠 TECHNICAL KNOWLEDGE (220-240 words)
The deeper technical explanation. This is WHERE you teach the actual engineering:
- How the technology/concept works at the systems level
- Key terminology defined precisely (no jargon without definition)
- Architecture diagrams described in prose (inputs → processing → outputs)
- Edge cases, failure modes, and constraints
- This section replaces the old "Teach Python from scratch" mandate — you teach the CONCEPT, not the language syntax

### Section 3: 📂 OUR CODE (100-200 words)
Point to the EXACT file(s) in the codebase (`cmf/`, `src/ccp/`, `cmf/apps/web/`).
- Annotate 2-3 critical sections with inline commentary explaining WHY the code does what it does
- Reference specific line numbers or function names where possible
- If code DOES NOT EXIST yet, state: `⚠️ BUILD REQUIRED — [description of what needs to be built]`
- If code EXISTS but needs extension, state: `🔧 EXTEND — [description of what to add]`

### Section 4: 🤖 AGENT PROMPT (50-150 words) — OPTIONAL
A ready-to-paste prompt for Pi, Claude Code, or Gemini CLI.
- The prompt must be specific to OUR codebase and this unit's build target
- Include the expected output format
- Mark as `⚠️ NOT YET — Code must be built first` if the target doesn't exist yet
- This section may be omitted ONLY if the unit is pure science/theory with no build target

### Section 5: ⌨️ TERMINAL (50-100 words) — OPTIONAL
Exact commands (AWS CLI, Docker, npm, git, etc.).
- One command per line
- No prose between commands — only inline comments with `#`
- Include expected output snippets where helpful
- This section may be omitted ONLY if the unit has no terminal-executable actions

### Section 6: ✅ IMPLEMENTATION STEPS (100-200 words)
Detailed step-by-step instructions for what to BUILD or CONFIGURE in this unit.
- Numbered steps (1, 2, 3...)
- Each step is a concrete, executable action
- Reference the exact files to create or modify
- Reference the agent prompt from Section 4 if applicable
- If the unit is pure science, this section describes what to READ and in what order

### Section 7: ✅ VERIFY (30-50 words)
The exact command, test, or observable outcome that proves the unit's work is complete.
- Binary outcome: pass/fail
- Must be a CONCRETE check, not "understand X"
- Example: `curl http://localhost:3000/api/health → 200 OK`
- Example: `pytest tests/test_pipeline.py → all green`

### Section 8: 🔗 BRIDGE (30-50 words)
What the next unit builds on from this one.
- One to two sentences maximum
- Must create a dependency — the next unit would feel incomplete without this one

**Total word count per unit: 700-1140 words.**

## 4B. THE OPERATIONAL ARCHITECTURE (CRITICAL CONSTRAINT)

> **THE CCP IS NOT 24/7. IT IS SCHEDULE-BASED.**

Both agents must internalize this architectural reality. Generating content that assumes always-on agents, persistent GPU instances, or real-time chatbot loops is a STRUCTURAL FAILURE.

### How the CCP Actually Operates:

1. **Scheduled Batch Processing:** Agents activate on TWO distinct schedules: 
   - **Coach content schedule:** Weekly generation batches where scripts are produced, recorded via Studio Block, and processed by CMF.
   - **Client accountability schedule:** PROGRAM-DEPENDENT voice tracking (e.g., 2-3x/week based on `PantryConfig`). It is NOT daily unless configured that way.
2. **Limited Interaction Sessions:** Client sessions consist of 3-5 messages maximum — a voice note in, a confirmation + follow-up out. This is NOT a continuous conversation.
3. **Voice Notes → Async Processing:** Clients send voice notes on THEIR schedule. The system processes async (STT → analysis → response generation → delivery). Not real-time chat.
4. **GPU On-Demand (Spot/Scheduled):** GPU instances spin UP for batch processing and spin DOWN when the batch is complete. We are NOT running $30/hr persistent GPU instances.
5. **Always-On = Dashboards Only:** Only these services run persistently:
   - Video Editor (Next.js) — accessible by URL
   - AFFiNE Dashboard — accessible by URL, has built-in AI functionality
   - API endpoints (FastAPI) — for dashboard↔pipeline communication
6. **Cost Implication:** The cost model is per-batch, NOT per-hour. This fundamentally changes GPU sizing, warm-up strategies, and billing calculations.

### What This Means for Content Generation:
- **Chapter 2 (NIM):** Cost model = batch GPU usage. Keep-Warm = scheduled pre-warm 5 mins before batch
- **Chapter 6 (Telegram):** NOT a chatbot. Scheduled voice tracking with PROGRAM-DEPENDENT cadence (e.g. 2-3x/week) and 3-5 message limits
- **Chapter 10 (Platform):** Telegram sends prompts matching the program `check_in_schedule`, NOT real-time conversation
- **Chapter 12 (Launch):** CRON schedulers manage TWO clocks: weekly coach content + per-client accountability
- **Harness Outputs:** By Chapter 12, the student must have built the 7 `ccp-*` commands (in markdown format, targeting Pi Coding Agent) that operate this entire schedule.
